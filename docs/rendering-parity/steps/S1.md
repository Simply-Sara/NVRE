# S1 — NIF header and block decode

| ID | Step | Check | Oracle | Status |
|---|---|---|---|---|
| S1-1 | **Every block of every NIF in the corpus re-encodes byte-identically.** This is the single highest-value measurement in the plan, and it has never been run | `nifsample` for the routine check (stratified by data subtree, ~540 files, ~90s per game); `nifreencode` for the exhaustive one (306,674 files, hours) | O1 | **fnv verified: 537 sampled files, 16,982 blocks, 0 mismatches.** fo3/skyrimle/skyrimse/fo4 sampled, see matrix |
| S1-2 | The version and `bs_version` distribution the game actually ships, per game | `nifreencode` prints both histograms per game; record them in `matrix.json` so a schema change that shifts a version band is visible | O1 | printed per game, to be written into the matrix |
| S1-3 | No block type in the corpus is `Unknown` to the schema | `niftypes` — reads only the header's type-name list, decodes nothing | O1 | **measured over all 306,674 files: fnv 0, fo3 4, skyrimle 0, skyrimse 2, fo4 37** |
| S1-4 | No block is `Short` (the schema consumed fewer bytes than the block holds) — that is the signature of a layout written for another game | `nifsample`'s short count, by type | O1 | fnv 0; the others sampled, see matrix |
| S1-5 | The string table resolves every field the schema declares as a string, and **nothing else** | unit test on the `resolve_strings` rule (a `scale` of 1.0 must not become a string); corpus count of fields resolved | O4 | rule tested, corpus count to write |
| S1-6 | A block whose type is declared in a family layer but whose `inherit` is missing decodes to the right values anyway — i.e. `lineage` is checked, not just decode success | corpus probe printing `dec.lineage` for every shader block, per game; the Skyrim `BSLightingShaderProperty` inheritance fix is the model for why | O1 | to write |

**Why re-encode first.** It is the only oracle that needs no external
reference, it already exists, and it judges the exact thing every later stage
depends on: whether the schema read the right layout. A block that decodes but
does not re-encode is a block whose fields are all shifted — and `shape_props`
will happily read `glossiness` out of what is really the emissive multiplier.

**The cache trap.** The resolved field lists and chains are cached, because
rebuilding them per block was most of the cost. A cache filled *lazily* is
therefore wrong: `Schema::merge` is called once per layer, and a cache built
after the base but before the version layer answers every later question from
the base alone. The symptom is not a wrong value but **zero fields** — a block
the version layer defines reads as having none, so it fails to decode at all.
Skyrim SE's `BSTriShape` found it: 61,597 blocks reported "no definition for
the block type" while the schema plainly defined it with 11 fields. The caches
are dropped in `merge`, and `a_layer_merged_after_a_lookup_still_applies` pins
the rule.

**What the sweep found.** Three checkers, each answering a different question:

| Checker | Question | Cost |
|---|---|---|
| `niftypes` | Which block types does the corpus use that the schema does not define? Reads only the header's type names, decodes nothing | exhaustive: all 306,674 files in ~10 min |
| `nifsample` | Do the blocks re-encode? Stratified by data subtree | ~540 files per game, ~90s |
| `nifreencode` | The same, exhaustively | hours; run before a release, not after every change |

The failures group into three classes:

1. **A block type the schema does not define at all** — Fallout 4's
   `BSLightingShaderProperty` at 1,170,607 uses, `bhkCylinderShape` in Skyrim
   SE, `bhkConvexListShape` in Fallout 3. These are S1-3's list, and each is a
   block the reader cannot read rather than one it reads wrongly. Fallout 4's
   is the largest single gap in the plan: every lit shape in the game.
2. **A block type the schema defines wrongly** — these decode `Short`, which is
   the signature of a layout written for another version.
3. **A block whose data the schema cannot express** — a Havok container whose
   length the schema has no field for, so the read runs past the block's end.

The sample is stratified by data subtree rather than drawn at random, because
a random draw over 20k paths lands mostly in whichever subtree is largest, and
a bug confined to `meshes\weapons` would be missed by chance.
