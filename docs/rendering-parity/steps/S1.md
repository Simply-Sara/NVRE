**Why re-encode first.** It is the only oracle that needs no external
reference, it already exists, and it judges the exact thing every later stage
depends on: whether the schema read the right layout. A block that decodes but
does not re-encode is a block whose fields are all shifted — and `shape_props`
will happily read `glossiness` out of what is really the emissive multiplier.

**The cache trap.** The resolved field lists and chains are cached, because
rebuilding them per block was most of the cost. A cache filled *lazily* is
therefore wrong: `Schema::merge` is called once per layer, and a cache built
after the base but before the version layer answers every later question from
the base alone. The symptom is not a wrong value but **zero fields** — a block
the version layer defines reads as having none, so it fails to decode at all.
Skyrim SE's `BSTriShape` found it: 61,597 blocks reported "no definition for
the block type" while the schema plainly defined it with 11 fields. The caches
are dropped in `merge`, and `a_layer_merged_after_a_lookup_still_applies` pins
the rule.

**What the sweep found.** Run `scripts/s1-check.sh`, which checks every
installed game against its own schema chain and writes one file per game. The
Fallout games are clean; the others are not, and the failures group into three
classes:

1. **A block type the schema does not define at all** — `bhkCylinderShape`,
   `bhkBallSocketConstraintChain`, and the Skyrim particle and controller
   types. These are S1-3's list, and each one is a block the reader cannot
   read rather than one it reads wrongly.
2. **A block type the schema defines wrongly** — `NiSkinPartition`,
   `NiPSysData`, `BSStripPSysData`. These decode `Short`, which is the
   signature of a layout written for another version.
3. **A block whose data the schema cannot express** — `bhkRigidBody` and
   friends read past the end of their block, which is a Havok container whose
   length the schema has no field for.
